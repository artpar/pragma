# Pragma Web Workbench

Pragma should not present itself as a better chat window. It should present itself as a **browser-based control room for autonomous software work**: a place where an engineer can define intent, set boundaries, watch execution, inspect changes, intervene when risk rises, and safely resume later. That recommendation follows both from the product brief you provided and from how the strongest adjacent products have evolved. GitHub Copilot cloud agent emphasizes research, planning, diff review, background execution, session tracking, cancellation, and pull-request iteration; Cursor emphasizes parallel background agents, web access, review, and self-hosted isolated environments; Claude Code exposes explicit permission modes, rule sources, checkpoints, sessions, cost controls, and context management; OpenHands differentiates on transparency, security, and model-agnostic control. In other words, the market is already converging on the idea that autonomous coding needs an **operational workspace**, not just conversation UI. citeturn21view7turn25view2turn30view1turn30view4turn22view0turn22view1turn22view3turn26view0turn21view8turn35view0turn35view1turn21view13

The trust model should also be explicit. Established human-AI guidance consistently says that users need visibility into system status, user control and freedom, clear explanations when confidence or capability matters, and feedback loops that let them steer the system over time. NIST’s AI RMF adds that transparency should make it understandable what happened, when, and by whom, especially when outcomes are adverse or require redress. For Pragma, that means the UI has to surface model activity, tool activity, permissions, file effects, retries, compaction, and sub-agent behavior as distinct things with distinct affordances. citeturn21view0turn21view1turn21view2turn21view3turn21view16turn21view17

## Signals from adjacent products

The most relevant product pattern is that **autonomous execution is being wrapped in plan-review-iterate loops**. GitHub’s cloud agent explicitly supports repository research, plan creation, iterative code changes on a branch, diff review, and later PR creation; its docs recommend reviewing and refining the work before opening a pull request. Cursor’s own best-practices guidance says the most impactful change is planning before coding, and its agent workflows notify the user when work is done so the user can review changes and merge. Claude Code similarly exposes plan mode, accept-edits mode, multiple permission modes, and checkpoint-based rewind. These are all strong signals that Pragma should make **planning and review first-class, not optional afterthoughts**. citeturn21view7turn25view2turn25view0turn26view0turn35view0

A second strong pattern is that **background work must remain visible and interruptible**. Cursor’s cloud agents can run many agents at once, continue while the user is away, and be accessed from the editor or from the web; GitHub exposes running and past sessions, status-at-a-glance, session logs, notifications, and cancellation; VS Code’s documentation for Copilot cloud agent makes the distinction explicit between background cloud execution and interactive local agent use. That matters because Pragma’s own model is session-centric and agentic: delegated work cannot feel like it disappeared into a black box. The user needs persistent cards, logs, and cancel/message controls for every active branch of work. citeturn22view0turn22view1turn30view1turn30view4turn30view3

A third pattern is that **permissions and safety controls need their own UI vocabulary**. Claude Code’s permission UI distinguishes allow, ask, and deny rules and shows the settings source; its permission modes make explicit tradeoffs between convenience and oversight; Anthropic’s engineering writeup on auto mode notes that users approve the large majority of prompts, creating approval fatigue if the system over-prompts. Outside coding agents, Android, Apple, Chrome, and NN/g all converge on the same lesson: request access only when relevant, explain why, time prompts in context, and allow reversal. For Pragma, the permission system is too central to bury inside a tiny modal. It deserves a rich inspection surface with scope, source, extracted risk content, and reversible decisions. citeturn21view8turn26view0turn25view1turn21view14turn28view0turn28view1turn15search1

A fourth pattern is that **observability UIs outperform transcript dumps when systems become multi-step and stateful**. Temporal stores complete event history for each workflow execution; Dagster’s UI differentiates structured event logs from raw compute logs; Prefect tracks the state lifecycle of each flow run; Step Functions and Stately both formalize workflows as state machines with explicit transitions. That is almost a direct blueprint for Pragma’s evidence stream requirement. The right mental model is not “chat history.” It is “runtime history.” citeturn21view4turn21view5turn21view6turn31view0turn31view1

## Recommended workspace architecture

The core screen should be a **four-zone workbench** that combines IDE conventions with observability conventions. VS Code and JetBrains both demonstrate why this is durable for developer tools: navigation and project context on the left, editing/primary work in the center, supporting tools on the side or bottom, and a status strip for global context. VS Code also specifically recommends using the status bar for workspace-level state, discrete background progress, and warnings, while cautioning against clutter. That maps cleanly to Pragma’s needs. citeturn27view0turn27view1turn27view2turn27view3turn27view4turn27view5

### Primary screen model

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ Top command bar: task • repo/worktree • provider/model • tools • permissions│
├───────┬──────────────────────┬──────────────────────────────┬───────────────┤
│ Act.  │ Session / run rail   │ Live operation canvas        │ Inspector     │
│ rail  │ Sessions • Agents    │ Typed turn stream            │ Contextual    │
│       │ Orchestration • MCP  │ Model • Tools • Files • Sys  │ permission,   │
│       │                      │ Filters + grouped events     │ diff, model,  │
│       │                      │                              │ raw event data│
├───────┴──────────────────────┴──────────────────────────────┴───────────────┤
│ Bottom dock: Diff • Validation • Files • Terminal/Logs • Audit/Event trail │
├──────────────────────────────────────────────────────────────────────────────┤
│ Status bar: branch • session • mode • MCP • context % • token/cost • errors│
└──────────────────────────────────────────────────────────────────────────────┘
```

This structure is doing three jobs at once. It preserves the familiarity of an IDE-style workbench; it creates enough space to separate different signal types instead of mixing them into a transcript; and it gives Pragma clear “attention zones,” so background progress can remain low-friction until it becomes important, at which point it escalates to the inspector or a blocking card. That follows established guidance on visibility of system status, user control, recognition over recall, and minimalist use of crowded navigation surfaces. citeturn27view0turn27view2turn27view4turn21view16turn21view17

### What each zone should own

The **activity rail** should be sparse and stable: Sessions, Agents, Orchestration, Files, MCP/Tools, Policies, Analytics. Do not place temporary run artifacts here. VS Code’s activity bar guidance is clear that it is a core navigation surface and should not be overloaded with one-off views. citeturn27view3

The **session/run rail** should act like a mission queue. It should list active sessions, paused sessions, failed sessions, delegated agents, and orchestration runs, each with small status badges and last-activity timestamps. Claude Code’s session model, GitHub’s running and past sessions, and Cursor’s background/cloud agents all imply that users need to jump between work items without losing continuity. Pragma should therefore treat sessions as persistent objects, not transient chat tabs. citeturn35view1turn35view2turn30view0turn30view1turn22view0turn22view1

The **live operation canvas** should be the heart of the product. The center is not a single transcript; it is a **typed turn stream**. Every turn should render as grouped cards, in this order: user intent, model response text, model reasoning/thinking, tool requests, permission checks, tool execution/results, file effects, validation output, and system/runtime events. Dagster’s distinction between structured event logs and raw logs is useful here: Pragma should default to structured cards with metadata and filters, while still allowing raw output inspection on demand. citeturn21view5turn21view16

The **inspector** should be contextual rather than generic. If the user selects a permission event, the inspector becomes a permission console. If the user selects a tool run, it becomes a tool detail panel. If the user selects a file effect, it becomes a semantic diff and patch review. If the user selects a retry or compaction event, it becomes an operational diagnostic view. This is the right place for “exact tool, exact scope, exact consequence,” which is central to both your brief and the external safety guidance. citeturn21view3turn21view8turn26view0turn28view0

The **bottom dock** should hold high-density supporting artifacts: diff, validation, file tree, raw command/log output, and full audit/event feed. JetBrains and VS Code both reserve bottom or side tool windows for run/debug/output surfaces. Pragma should use that same convention because it keeps the center readable while still making operational detail one click away. citeturn27view0turn27view5

## Interaction patterns for trust and control

The top task composer should behave less like a chat box and more like a **run configuration bar**. The user should be able to set intent, current worktree, provider/model, max tokens, temperature, thinking mode, structured-output schema, permission mode, and allowed toolset before launching. Existing agent systems already expose pieces of this configuration: Claude Code exposes permission modes directly in the UI; Cursor and GitHub expose agent selection and cloud delegation; OpenHands makes user-facing configuration part of its web UI; Anthropic and Google both document that rate limits, spend limits, context windows, and long-context behavior materially affect how a run behaves. Because Pragma is provider-generic, these settings should be visible at launch and throughout the run, not hidden in preferences. citeturn26view0turn21view13turn30view3turn16search15turn21view18turn21view19turn12search1turn12search8turn33view1

A **plan-first path** should be the default for anything medium- or high-risk. The UI should offer two explicit launch actions: **Plan** and **Run**. If the user chooses Plan, Pragma shows the proposed approach as an artifact that can be edited, approved, or rejected before tool execution begins. This mirrors Claude Code’s plan mode, Cursor’s plan mode, and GitHub’s research-plan-iterate workflow. It also gives the user a natural place to refine scope and constraints before tokens, file edits, or external tools accumulate risk. citeturn26view0turn6search6turn21view7turn25view2

Permission handling should be the single most carefully designed interaction in the product. A permission card should show: the exact tool and parameters, impacted paths/targets, extracted risk content, why the request happened now, any matching rule and its source, and the consequences of approving. The action choices should be richer than Allow/Deny: **Allow once**, **Allow for this turn**, **Allow for this session**, **Create project rule**, **Deny once**, **Block with rule**, and **Edit the proposed command or scope**. Android, Apple, Chrome, and NN/g all emphasize contextual timing, user-understandable rationale, least privilege, and decision reversal; Claude Code’s permissions UI already demonstrates the value of exposing rule sources and permission modes. Pragma should borrow that clarity and make revocation obvious from the Policies area. citeturn21view14turn28view0turn28view1turn15search1turn26view0turn21view8turn25view1

File review should be a **grouped patch workflow**, not a flat list of changed files. Group changes by session, turn, and originating tool call; then let the reviewer drill from group summary to file to hunk. GitHub code review and Copilot code review both emphasize line-linked suggested changes that can be applied with a couple of clicks, while Cursor’s ecosystem emphasizes review before acceptance and end-to-end work for later inspection. For Pragma, each group should include a semantic explanation, validation status, and freshness label so the user can distinguish “last tool changed this five seconds ago” from “this file was edited by an earlier turn and is now stale relative to current workspace state.” citeturn8search3turn25view3turn25view2turn23search13turn22view3

Delegated agents need their own **agent cards**. Each card should show owner, current task, branch/worktree, current phase, last activity time, last tool invoked, current token/cost estimate, errors, and two persistent controls: **Cancel** and **Message agent**. This is directly supported by how Cursor and GitHub talk about background jobs: run while you are away, see status at a glance, inspect logs, receive notifications, and cancel if needed. I would make the agent board a first-class left-rail destination and also pin active agent summaries into the session rail. citeturn22view1turn22view0turn30view1turn30view4

## Event, audit, and recovery views

Pragma’s evidence stream should become an **event-first timeline**, with transcript as just one projection. Temporal stores complete workflow event history; Dagster streams structured event logs and raw logs separately; Prefect tracks each run’s state lifecycle; Step Functions and Stately show how explicit states and transitions make complex workflows easier to reason about. For Pragma, the audit surface should therefore filter by event type: Model, Tool Request, Permission, Tool Result, File Effect, Retry, Compaction, MCP, Agent, Error, Session, and Orchestration. Clicking an event should reveal its causal chain: what led to it, what it changed, and what happened next. citeturn21view4turn21view5turn21view6turn31view0turn31view1

Operational states should be concrete, not cosmetic. “Retrying provider,” “compacting context,” “rate limited,” and “model context window exceeded” all deserve explicit visual treatment with cause, mitigation, and what the system did automatically. Anthropic’s docs note that the context window acts like working memory, that larger context can degrade through “context rot,” and that generation can stop when the context window is exceeded; Claude Code’s cost docs describe auto-compaction, status-line usage visibility, and usage/cost breakdowns. Those realities justify a persistent **context and budget strip** in the status bar, plus event cards when compaction, rate limiting, or overflow actually happens. citeturn21view18turn21view19turn10search1turn16search15turn33view1turn27view2

Session recovery should center on **what happened, what changed, what remains, and whether it is safe to continue**. Claude Code stores sessions continuously, supports resume and branching, and keeps checkpoints that can restore code, conversation, or both; GitHub lets users query session history across synced sessions; Copilot CLI also recommends fresh sessions when compactions accumulate and context is losing fidelity. Pragma should translate those mechanics into a recovery sheet shown whenever a session is resumed after meaningful inactivity or after an error. That sheet should summarize last goal, files changed, pending todos, unresolved blockers, current branch/worktree, permission mode, and whether the workspace drifted since the last turn. citeturn35view0turn35view1turn35view2turn30view0turn35view3

For organizations, Pragma should include an **audit export** that is structured enough for SIEM and compliance use. GitHub recommends streaming Copilot audit logs to a SIEM for long-term history and alerting; Claude Code surfaces cost tracking and team spend limits; Cursor exposes analytics for teams. That suggests a clean separation between the operator-facing session timeline and an admin-facing export/reporting surface. The operator sees what is necessary to supervise work in real time; the organization gets durable, queryable audit artifacts later. citeturn30view2turn33view1turn32search2

## Supporting views beyond the main workbench

The main workbench should handle most daily use, but Pragma also needs three supporting views.

The **Orchestration view** should be a statechart-first page that only appears when orchestration is active. Use a finite-state graph with current state highlighted, prior transitions dimmed, and active artifacts/hand-offs visible as side panels. Step Functions and Stately make a strong case for visual state machines when workflows are event-driven and multi-branch. For Pragma, this is the right surface for personas, control states, handoffs, transitions, and produced artifacts. It should not replace the main run timeline; it should complement it. citeturn31view0turn31view1

The **MCP and tool registry view** should show connection health, auth state, exposed tools/resources, latency or last-seen health, and whether each server/tool is currently loaded into context. MCP is specifically about exposing external systems, tools, and workflows to AI applications, and Claude Code’s MCP docs show practical examples ranging from issue trackers to monitoring dashboards and Figma-backed design updates. Because these extensions change the product’s effective action surface, they deserve visible health and scope controls, not a buried settings screen. citeturn26view1turn26view2turn24search3

The **Session library** should feel closer to an engineering casebook than a chat history page. It should support search by task, repository, agent, changed file, model/provider, cost, and outcome. Claude Code and GitHub both expose resume/query patterns that treat sessions as recoverable work objects rather than disposable conversations. Pragma should go one step further by letting users pivot from a session into its file effects, permission history, and final artifacts. citeturn35view1turn30view0turn34search7

## Design principles and anti-patterns

The most important principle is **typed separation**. Model text, model reasoning, tool requests, tool results, file changes, and runtime/system events should never be visually conflated. The reason is not aesthetics; it is trust calibration. Users make better decisions when they can tell whether the system is proposing, explaining, acting, or reporting. That principle is strongly aligned with human-AI interaction guidance and with the structured-log patterns seen in workflow systems. citeturn21view0turn21view1turn21view2turn21view5

The second principle is **progressive disclosure without operational opacity**. The default view should stay calm, but any meaningful state should be inspectable within one click. VS Code’s guidance on sidebars and status bars warns against clutter, while its progress and warning patterns show how to escalate attention appropriately. For Pragma, the right pattern is: small badges for low-risk background activity, inline cards for important status changes, blocking sheets for permission/risk decisions, and deep inspectors for forensic detail. citeturn27view2turn27view4turn21view16

The third principle is **design for reversal**. Claude checkpoints, session branching, GitHub PR iteration, and permission-reversal guidance all point the same direction: users must be able to step back without losing the story of what happened. So Pragma should make undo, rewind, branch, cancel, and rule revocation part of the main interaction model. Hidden reversibility does not build trust; visible reversibility does. citeturn35view0turn35view2turn25view2turn28view0turn21view17

The main anti-patterns to avoid are straightforward. Do not ship a transcript-centric UI that makes tools and file effects feel secondary. Do not collapse permissions into generic “approve action” prompts. Do not hide provider retries, compaction, or over-context conditions behind a spinner. Do not make background agents invisible. Do not treat orchestration as a giant unreadable flowchart on the main screen; keep it in a specialized view with links back to run evidence. And do not make the audit view a raw dump when typed events can be filtered, grouped, and correlated. Those are exactly the failure modes the broader ecosystem has been compensating for. citeturn21view5turn21view6turn25view1turn30view4turn31view0

## Open questions and limitations

This concept is grounded in your product brief plus public patterns from adjacent tools and HCI guidance, but a few design questions remain open.

The first is **how much native code editing belongs in the browser**. The research supports diff review, file inspection, and lightweight edits in web surfaces, but it does not by itself answer whether Pragma’s web UI should become a full editor versus a supervisory workbench that pairs with local IDEs. GitHub, Cursor, and Claude all support different points on that spectrum. citeturn30view4turn22view1turn26view0

The second is **how much reasoning should be exposed by default**. Your brief says to separate model reasoning/thinking, and I agree; however, the default should probably be collapsed summaries with explicit expansion, because the primary supervision tasks are usually scope, permissions, file effects, and runtime state rather than long-form reasoning text. That is an inference from the trust-and-control literature and from how modern agent tools emphasize plans, diffs, and operational logs over uninterrupted reasoning streams. citeturn21view1turn21view2turn21view16turn25view2

The third is **how far Pragma should go on team and admin surfaces in the first release**. The public landscape shows strong value in analytics, spend limits, audit exports, and enterprise controls, but your brief does not specify RBAC, approval chains, or collaboration requirements in detail. If those are near-term priorities, the policy, analytics, and audit surfaces should be elevated earlier in the roadmap. citeturn33view1turn32search2turn30view2

If I compress all of the research into one design sentence, it is this: **Pragma should look and behave like an engineering operations console wrapped around an autonomous agent runtime, with chat demoted to one signal among many.** That is the clearest match to the product you described, the clearest path to user trust, and the clearest differentiation from transcript-first coding tools.
